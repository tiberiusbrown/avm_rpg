# Tiled and 16x16 asset pipeline

Install `tools/requirements.txt`. Tiled is needed for visual map editing; XML and
Pillow suffice for regeneration. Run `python tools/generate_assets.py`, or use
`--check` to compare generated bytes. CMake tracks TMX, TSX and PNG inputs. The
generator also writes `assets/images/<SYMBOL>_preview.png`, a 1x preview of each map with
every tile drawn from its atlas cell at 16x16 pixels; unpainted outside cells are gray.
It also writes `assets/images/OUTDOOR_world_map.png`, the monochrome exterior overview
at one pixel per tile. Region patterns are anchored in map coordinates: dotted woodland,
checkerboard water, solid roads and bridges, building silhouettes with door notches, and
sparse rock and cliff marks. Grass and minor objects are omitted. The same image is packed
as `WORLD_MAP_SPRITE` in `sprites.cpp`, with two dimension bytes followed by page-major
bitmap bytes; only the last eight-pixel page needs padding. The current 240x248 map uses
7,440 bitmap bytes and is clipped directly from program memory by the sprite renderer.
For tile meanings and map design rules, see `assets/maps/AUTHORING.md`, and
`AUTHORING_INTERIOR.md`, `AUTHORING_CAVE.md` and `AUTHORING_DUNGEON.md` beside it.

## Terrain and indices

Use finite orthogonal right-down TMX maps, 16x16 tiles, uncompressed CSV layers,
and one external tileset from `assets/tilesets`. The maximum logical area remains
240x248 tiles. Map data stores exactly width * height tile IDs in row-major order,
without chunk padding. The 8x4 chunks organize handler dispatch only.
Layers flatten in document order; zero GIDs leave underlying tiles untouched.
Empty cells become the outside sentinel, 255. No flipping, rotation, infinite/compressed maps, offsets,
hidden/translucent layers or Tiled tile animation is supported. Animation frames come from
layer atlases instead; see [Animation](#animation).

**Each map uses exactly one tileset, and the game selects the tileset by area.** A map
with two tileset references is rejected. Outdoor maps use `world.tsx` with
`tiles16.png`. `interiors.tmx` uses `house.tsx` with `tiles16_house.png`, `cave.tmx` uses
`cave.tsx` with `tiles16_cave.png`, and `dungeon.tmx` uses `dungeon.tsx` with
`tiles16_dungeon.png`. The TSX `name` attribute names the tileset in generated
code and must be a lower-case identifier.

Every atlas is opaque monochrome, 256x256, with 16 columns and 16 rows. Runtime
ID equals `row * 16 + column` within its tileset: in the world tileset the top-right
cell is 0x0F and the sign is 0x41. A TSX declares all 256 cells, with `reserved=true` as
the only property on cell 255. The exporter excludes that cell from runtime tiles and
sprite frames; TMX GID 256 with firstgid=1 is rejected. Usable cells have explicit
`runtime_id` 0..254, unique `symbol`, an int `collision` mask from 0 to 65535, and a bool
`portal` property. `assets/maps/AUTHORING.md` describes the mask: terrain that fills its
cell is fully solid, and an object takes a simple convex shape that roughly covers its art. Blank black cells
remain valid indexed frames and are not deduplicated or removed. Unused cells
default to full collision (65535); mark new terrain deliberately when authoring.

Tilesets in use get runtime indices: `world` is 0, and the others follow by name, so
`cave` is 1, `dungeon` is 2 and `house` is 3. The generator emits:

- `area_ids.h`: `TILESET_<NAME>` indices, `TILESET_COUNT` and
  `constexpr uint8_t area_tileset(uint8_t area)`, a switch over the areas.
- `tile_ids.h`: `TILE_<symbol>` for the world tileset and `<NAME>_TILE_<symbol>` for each
  other tileset, such as `HOUSE_TILE_FLOOR_WOOD_A`.
- `map_assets.cpp`: `TILE_COLLISION`, one 256-entry block per tileset, read at
  `(area_tileset(game.area) << 8) | tile`. Entry 255 of each block is the solid sentinel.
- `sprites.cpp`: `TILE_SPRITES` and one `<NAME>_TILE_SPRITES` sheet per other tileset,
  with `tileset_sprites(tileset)` to select one. `rpg_render_world` draws with the sheet
  of the active area.

Only tilesets that a map references are emitted. The generator still parses every TSX in
`assets/tilesets` and writes `assets/images/<atlas>_collision.png` for each one, so an
unused tileset stays valid.

Each 16x16 tile occupies 32 bytes: 16 top-page columns, then 16 bottom-page columns.
Within a byte, bit zero is the uppermost pixel. Each tileset's sprite array begins with
width=16, height=16, followed by the frames in runtime-ID order. A sheet stops after the
highest tile of its tileset that has art in any layer or that a map paints, so it holds
fewer than 255 frames (`tile_export_counts()` in the generator). The tiles above it are
blank and unused, and `TILE_COUNT` still counts the whole atlas. `tile_ids.h` gives the
frame count as `<PREFIX>TILE_SPRITE_COUNT`, which `tile_wind_frames()` uses as the wind base.

## Animation

`assets/maps/AUTHORING.md` describes the authoring rules. The generator's part:

- **Phase layers.** `<atlas>_phase1.png` to `<atlas>_phase3.png` are optional 256x256 RGBA
  images in the atlas layout. A cell is fully transparent or fully opaque monochrome, and
  cell 255 stays transparent. `sprites.cpp` gets one more sheet per phase, with the same frame count as the atlas sheet,
  `<NAME>_TILE_SPRITES_PHASE<n>`, in which a transparent cell repeats the atlas frame.
  `tileset_phase_sprites(tileset, phase)` returns the sheet, and a phase whose frames all
  match an earlier sheet returns that sheet. Each sheet takes 32 bytes of read-only data per frame, plus two header bytes.
- **Wind layer.** `<atlas>_wind.png` has the same format. Its frames follow the exported
  atlas frames in the tileset's first sheet as one block that spans the tiles with a wind frame.
  `tile_wind_frames(tileset)` in `area_ids.h` gives the block as first tile, count and first
  sheet frame. Exactly the tiles of the ambient classes `grass` and `flowers` have a frame.
- **Ambient classes.** The optional string tile property `ambient` is one of `none`, `grass`,
  `flowers`, `water`, `tree`, `floor`, `perch`, `road`, `steam`, `cave`, `crypt`, `drip`,
  `pool`, `crystal` and `ember`. `area_ids.h` gets the
  `AMBIENT_CLASS` enum and `tileset_has_ambient()`, and `map_assets.cpp` gets `TILE_AMBIENT`,
  one byte per tile in 256-entry blocks like `TILE_COLLISION`.
- **Sky.** The bool tileset property `sky` is the only tileset property. It generates
  `tileset_has_sky()`, which lets birds fly over the tileset's maps.
- **Ambient sprites.** `ambient16.png` holds 16x16 plus-mask frames in rows of eight. The
  blank cells after the last frame are dropped, and `sprites.cpp` asserts that the count
  matches `AMBIENT_FRAME_COUNT` in `src/ambient.h`.
- **Title screen.** `title_scene.png` is the whole 128x64 background, opaque black and white,
  exported as `TITLE_SCENE`: sky, castle, bridge, water and the near bank, without the flag.
  `title_logo.png` is the game's name with its outline as opaque black and everything else
  transparent, exported as the plus-mask sprite `TITLE_LOGO`. `title16.png` holds 16x16
  plus-mask frames in rows of eight, exported as `TITLE_SPRITES`; the blank cells after the
  last frame are dropped. The foreground is separate plus-mask pictures drawn over the
  background, so creatures can pass behind them. `title_pine_small.png`, `title_pine_left.png`
  and `title_pine_right.png` are one pine each, with a height that is a multiple of eight rows;
  they are exported as `TITLE_PINE_SMALL`, `TITLE_PINE_LEFT` and `TITLE_PINE_RIGHT`, sheets
  whose frames are the picture's bands of eight rows from the top, which the title shifts apart
  to sway the tree. A pine may be wider than the part of it on screen, so that a leaning tree
  does not show a cut edge. `title_rock.png` is exported as the single frame `TITLE_ROCK`.
  `sprites.cpp` asserts the frame count, the logo size and each pine's band count against
  `src/title.h`, which also holds the screen positions that the animation uses (the layers,
  stars, flag, water, perch and paths).

## Actors

`actors16.png` is 192x512 RGBA: 12 columns and 32 character rows. Every row has
three north, three east, three south and three west frames. Zero-based pose 0
is standing; walking uses offsets 0,1,0,2. Each pose lasts eight simulation ticks.
`actor_frame()` shares this selection between player and NPC rendering. The
player uses row 0; `NpcDefinition::sprite_row` selects an NPC's row (0..31).

Rows 0-15 are people; `assets/images/actors16_descriptions.md` records each row's
sex, hair and head covering for portrait art. Rows 16-31 are
creatures and enemies:

| Row | Character | Row | Character |
| --- | --- | --- | --- |
| 16 | Giant rat | 24 | Zombie |
| 17 | Wolf | 25 | Ogre |
| 18 | Giant bat | 26 | Goblin |
| 19 | Giant spider | 27 | Ghost |
| 20 | Giant beetle | 28 | Mushroom creature |
| 21 | Snake | 29 | Floating eye |
| 22 | Slime | 30 | Golem |
| 23 | Skeleton | 31 | Hooded cultist |

Creatures follow the same frame layout. West frames mirror the east frames, and a
character keeps the same head and body proportions in all four directions. Creatures
that do not step animate their two walking poses another way: the slime squashes and
stretches, the bat flaps, and the ghost and floating eye bob.

The sheet's height sets the row count: append whole 16-pixel rows to add characters,
then update `ACTOR_ROW_COUNT` in `src/rpg.h`. The generated `sprites.cpp` asserts that
the two agree.

Opaque pixels must be black/white and alpha must be 0 or 255. Each actor frame
occupies 64 bytes: bitmap and mask bytes interleaved in page-major order. Alpha
alone defines opacity, so opaque black pixels erase underlying terrain while
transparent pixels preserve it. Each frame has its own mask. No standalone
`actor_mask.png` is used.

### NPC faces

`faces32.png` is the portrait sheet for dialogue: opaque black and white 32x32 frames
in two columns, 64x128 for the four current IDs. Row `n` is the face of `NPC_ID` `n`
(`NPC_NONE` is row 0); column 0 has the mouth closed and column 1 has it open, so a
speaking NPC alternates them. The open mouth keeps the closed mouth's width and is
three rows tall, and the jaw drops two rows with it. Faces follow the NPC, not its
sprite row, so two NPCs on one row can have different faces. Each face is drawn from
scratch to match its sprite's sex, hair and head covering (see
`actors16_descriptions.md`), and a row with no portrait is solid black. Facial features
share one grid in every face: eyes are three pixels wide on rows 15-16 at columns 11-13
and 18-20, the nose ends on row 18, and the closed mouth is columns 14-17 of row 21. Every figure
has a thin white line around its black outline, so skin and cloth read as a white fill,
a black line, then the white line, and dark masses such as hair are black inside that
white line. Append whole 32-pixel rows when adding portraits. `tools/generate_assets.py` emits the
sheet as `FACE_SPRITES` (frame `NPC_ID * 2 + open`) with a `FACE_PRESENT` byte per portrait row, and
exports `FACE_ROW_COUNT`, independent of `NPC_ID_LIMIT`. Identities outside the portrait
range use text dialogue. The dialogue overlay draws it above
the panel (see `docs/essential_npcs.md`). See `assets/images/AUTHORING_FACES.md` for how to
draw a face.

### Dialogue prompt indicators

`dialogue_prompts7.png` is 28x7: four opaque black and white 7x7 frames side by side. Frames 0
and 1 are the A button filled and outlined, which blink after the last page of a dialogue.
Frames 2 and 3 are a down arrow in two positions, which bobs at a page that more text follows.
The generator emits them as `PROMPT_SPRITES` and checks the frame count against
`PROMPT_FRAME_COUNT` in `src/rpg.h`. The overlay draws one at the right end of the last text
line when A starts to work.

## Positions and native handlers

Each map declares unique byte `area_id`, C++ `symbol`, and `spawn` referencing
one named, passable, handler-free tile in that area. Spawns are sprite pixel
origins: tile (7,5) is pixel (112,80).

Use Logic/Locations object layers with no type/class. Point centers are
`(16*tx+8,16*ty+8)`; fractional points select their containing tile. Rectangles
cover every tile with positive-area overlap, with exclusive right/bottom edges.
The name is optional and must be a unique C++ identifier when supplied. The only
optional property is `handler`, naming a native function.

Named single tiles generate `positions::Name`; rectangles generate row-major
`positions::Name_0`, etc. Named rectangles additionally expose a `NameRegion`
query value. Unnamed handlers use private constexpr positions. Each covered
tile dispatches exactly once from its own 8x4 chunk. Moving a point across a
chunk boundary automatically relocates its generated call.

The exporter emits `Handler<POS, STAGE>` and empty defaults for every authored
handler name. Add ordinary overloads in `handler_impl`, after including
`handler_defaults.h`:

```cpp
template <TilePos POS> void read_sign(Dialogue<POS>) {
    if(player_just_interacted<POS>())
        dialogue_show(F("Welcome to Nocturne Grove."));
}
```

The overloads live in `src/logic/`, one header per environment (`area_village.h`,
`area_cave.h`, `area_dungeon.h`), and `handlers.h` only includes them. `mechanisms.h` holds what
the environments share: the lever, plate, door and chest handlers read each area's
`AreaMechanisms` table, whose rows give every cell a mechanism kind (what it is, how the player
works it and what it sounds like), and operate it through one shared function that plays the change.
`show_message` shows the words that the area's `AreaMessages` table lists
for a sign or a plaque, and `take_passage` reads the `AreaPassages` tables. A marker that does more than these gets a handler
name of its own in the map and its overloads in its environment's header. A cell that is missing
from its table fails to compile.

Overload `Gameplay<POS>`, `Tiles<POS>` or `Dialogue<POS>`. Finish the entire
gameplay pass, reload the baseline cache, finish all tile handlers, then run
dialogue. Generated dependent calls use ADL; do not qualify them. New named or
unnamed handlers compile with their empty defaults before behavior is written.
Blocking interactions belong to Dialogue. Runtime terrain reads stay cache-only.

`player_just_interacted<POS>()` advertises an A hint and consumes a fresh A edge
only while facing the adjacent foot-center tile. Held A and diagonal targets do
not interact. `player_is_walking_onto<POS>()` recognizes actual tile entry.
`teleport_player<TARGET>(facing=STILL)` uses 16-pixel tile origins and preserves
facing when STILL. It validates bounds and clears the NPC pool/input; destination
tiles are rebuilt before destination gameplay runs on the next frame.

Optional Routes layers contain named polylines, `mode=once/loop/reverse` and
integer `pause` 0..255. Points must lie inside tiles, not on their edges. Export
assigns route IDs by sorted name and stores two-byte tile coordinates in PROGMEM.
The outdoor map has no routes; native fixtures exercise the generic system.

## Build and verification

```powershell
python tools/generate_assets.py --check
./tools/build.ps1 -SdkRoot ../../build/avm-sdk-install
ctest --test-dir build -C RelWithDebInfo --output-on-failure
cmake --build build --config RelWithDebInfo --target rpg_integration
cmake --build build --config RelWithDebInfo --target rpg_integration_full
python tools/collect_evidence.py --build build --write-docs
```

`build.ps1` initializes the MSVC environment matching the configured compiler.
Keep RelWithDebInfo and guest full LTO. For native-only builds pass `-HostOnly`.
Full-device QA requires matching `AVM_SOURCE_ROOT` and `AVM_BUILD_ROOT`; SDK-only
builds still run LLDB guest probes and source profiles, with device QA explicitly
skipped. `rpg_integration` runs distinct collision masks, validates every tile lookup
against TSX metadata, exercises device smoke scenarios, and records 100 ms profiles.
`rpg_integration_full` enables the exhaustive collision matrix, full normal/FXC device
QA and 8-second profiles. Use the full target before collecting evidence; the collector
reads `build/latest-full-verification.txt`, independently of subsequent fast runs.
Each integration run records stage times in `results.json` and prints them as it runs.
The default build refreshes root `rpg.arduboy` and builds the marker-bearing
`build/artifacts/rpg_qa.arduboy` that device QA reads.

## Compile-time chunk catalogs

The exporter writes `map_handler_catalog.h`, not a C++ dispatch implementation. Its
`AllMapHandlers` type list preserves map object order, rectangle expansion, overlapping
operations and private unnamed points. Operation tags call the existing generated
`Handler<POS, STAGE>` API. Empty fallback overloads return a marker so C++ can detect
actual stage implementations. New names compile safely before handwritten logic exists.
`world_assets.h` also exports area IDs, tile dimensions and chunk dimensions as constexpr
metadata, validated against Tiled. All flattened indices use at least 16 bits.

`src/chunk_dispatch.cpp` builds stage-specific dense PROGMEM tables and retains only
occupied chunk functions. NPC spatial sites come entirely from C++ `NpcPolicy` declarations;
Python has no NPC policy knowledge. Native fixture compilation uses its own generated
catalog and defaults, including unimplemented named and unnamed operations.
